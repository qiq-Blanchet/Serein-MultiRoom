## 1. 一句话目标

**让任意数量的 AI 各自拥有一套完整且相互隔离的 Serein 记忆系统，用户通过一个网站、一个统一网关及 VPS 管理入口集中创建、配置、备份与更新这些独立房间。**

这不是把一个数据库简单增加 `room_id` 字段，也不是让几个 AI 共用一份记忆后再做过滤。**一个房间 ≈ 一个完整、独立运行和独立保存数据的 Serein 实例**；多个实例复用同一套程序代码／镜像版本，由统一管理层编排。

系统最初可能只有三个 AI，但**不得把房间数量、AI 名称、房间 ID 固定为三个**；以后必须可以按需增加、暂停、恢复和管理新房间。

## 2. 已确定、必须遵守的产品决策

1. **动态房间**：房间数量可变；能够通过管理网页创建，亦应提供 VPS/CLI 创建途径。创建后自动注册该房间的路由与服务；不需要为每一个新房间复制修改一套 Python 工具源代码。
2. **每房间完整功能**：每个 AI 获得 Serein 原版已有的完整记忆能力，包括但不限于聊天网关、原话存档、Event、Scene、召回及冷却、索引、叙事卷、日记、暗房、梦境、窗影、备忘、自动摘要与后台 Agent 流水线、可选扩展和 MCP；具体功能仍依原版开关及模型配置决定是否运行。不得把某些房间降级为只有一部分记忆功能。
3. **硬隔离，不共享房间**：各房间的记忆、日记、梦境、历史、索引、后台状态、配置和备份相互独立。**不设计跨房间共享数据库、共享记忆、联邦搜索、公共房间或相互访问功能**。若不同 AI 都需要记住一件事，允许它们分别记录。
4. **两套开关保持独立**：Serein 既有「功能开关」与「MCP 工具权限」是不同层次，必须分别按房间管理。禁用某项 MCP 工具不代表清除数据或关闭对应后台功能；关闭后台功能也不应由 MCP 权限绕过。
5. **主人决定工具权限**：每个房间的 MCP 工具可见性与调用权限由管理员单独设置。工具初始权限由管理员控制，不得在没有允许的情况下让新 AI 获得跨房间权限。以服务器端为准，不能仅在网页隐藏按钮。
6. **统一管理网站**：同一网站中有房间列表与当前房间切换入口。切换后使用对应房间的完整 Serein 管理页面/功能页；管理操作必须始终绑定明确的房间上下文，不混用不同房间的数据。
7. **统一对外网关，分房间鉴权**：每个房间拥有稳定且唯一的 `room_id` 和独立的 Gateway/API Key、MCP 认证身份。由可信服务端认证结果决定房间，不能信任客户端自己填写的房间 ID 作为授权证明。
8. **新房间默认复制配置，不复制私人数据**：创建时默认以**第一个房间（或用户指定的默认模板房间）**为配置源；也可选择任意现有房间或全新空白。复制的目标是模型列表、上游参数、任务模型选择、功能配置、MCP 工具权限模板等**可复用设置**。绝不复制任何记忆、日记、梦境、原话、索引任务状态、召回冷却、个人资料、身份相关内容或原 Gateway Key。模型供应商的秘密凭据是否复用要提供单独、清晰的选项，管理员有控制权；初始交互可默认勾选复用，但需在创建前明确显示。
9. **独立备份与恢复**：每房间分开备份、列出、下载、恢复，避免任何文件或恢复目标混淆。恢复操作必须检查来源和目标房间身份、数据库/应用版本，默认只允许恢复到原房间；不能按显示名称猜目标。更新前要做完整备份。
10. **同步代码更新，隔离任务运行**：所有房间使用同一受控版本的 Serein 程序/镜像，便于一键更新。更新按房间分批进行、逐一健康检查；各房间的自动摘要、索引、后台队列与失败状态不互相覆盖。共享 VPS 的 CPU、内存、网络以及第三方模型配额仍是有限资源，须有资源限制和并发控制。
11. **尊重原版和可持续合并**：尽量不改动 Serein 原有记忆检索、证据、Event/Scene 生命周期、Writer、摘要策略。多房间逻辑尽可能放在部署编排、控制层、路由层、房间配置层；保留与原作者上游同步更新的能力。
12. **先小步测试，不直改真实数据**：开发和自动测试使用空白库或合成数据。未经管理员明确操作，不连接或迁移正在使用的私人 Serein 实例，不触碰真实密钥或私密聊天记录。

## 3. 非目标（明确不做）

- 不做多个 AI 的公共房间、记忆共享、跨房间全文检索或知识合并。
- 不按模型名称自动认定 AI 身份；一个模型可能在多个房间使用，模型不是身份。
- 不让单纯的 `X-Serein-Room-ID`、`X-Serein-Window-ID` 或请求体字段决定访问权限。
- 不在数据库里为所有资料打 `room_id` 然后让所有房间共用一份物理主库（首选物理隔离）。
- 不为每个房间维护不同的 Serein 程序分支或单独拷贝整份源码。
- 不在第一版实现多人管理员、团队协作、房间之间授权传递、复杂计费或多节点分布式调度。
- 不牺牲原版已有能力去简化 MCP：最终目标是每房间原版功能与接入方式的等价支持。

## 4. 架构（建议的实现边界）

```text
                        用户／管理者
                             │ 网页管理会话
                   ┌─────────▼─────────┐
                   │ 统一管理网站 / 控制层 │
                   │ 房间列表、创建、状态  │
                   │ 权限、备份、更新      │
                   └─────────┬─────────┘
                             │ 管理内部编排
AI 客户端 ─── Chat API / MCP ──▼─────────────┐
                   │ 统一 API / MCP Gateway │
                   │ 认证 Key / OAuth      │
                   │ 解析 room_id 并转发   │
                   └───┬────────┬────────┬──┘
                       │        │        │
                 ┌─────▼──┐┌────▼───┐┌───▼─────┐
                 │room A  ││room B  ││room ... │
                 │Serein  ││Serein  ││Serein   │
                 │完整服务││完整服务││完整服务 │
                 ├────────┤├────────┤├─────────┤
                 │独立 DB ││独立 DB ││独立 DB  │
                 │独立索引││独立索引││独立索引 │
                 │独立任务││独立任务││独立任务 │
                 │独立备份││独立备份││独立备份 │
                 └────────┘└────────┘└─────────┘
```

**首选方案：** 控制层维护房间注册表，每个房间拥有独立的 Serein `memory` 运行服务、配置、运行目录、秘密凭据、数据文件和后台作业生命周期；共享不可变的应用代码/镜像以及管理前端资源。使用 Docker Compose / Docker 编排优先实现 VPS 方案，也可以逐步提供本机进程模式。房间服务仅在内部网络监听；**不要给每个房间暴露公网服务端口**。

**注意：** 独立数据库不能自动保证 CPU、内存、第三方 API 限额互不影响。资源隔离需要进程/容器限制、并发上限、队列背压和超时。

### 4.1 房间注册表（控制层元数据）

建议字段（实际 schema 可调整）：

```yaml
room_id: "stable-immutable-id"       # 永久身份，不能随显示名称变化
name: "小玑"                         # 可修改的显示名称
created_at: "..."
state: "creating|ready|stopped|updating|error|restoring"
config_source_room_id: "...|null"    # 仅作创建审计，不是运行时依赖
runtime_dir: "..."                  # 每房间独立且安全校验的路径
service_id: "..."                   # 可观察的容器/服务标识
app_version: "git-sha-or-image-tag"
credential_reference: "..."         # 指向安全凭据存储，不能存明文在公开表
```

注册表只放房间的**管理元数据**；不要集中保存原话/日记/记忆正文。管理层必须支持崩溃恢复、并发创建幂等、失败后清理不完整资源、服务发现与状态对账。

### 4.2 建议的持久目录（仅示例）

```text
runtime/
  control/
    rooms.sqlite                # 房间注册元数据；不放私人记忆
    secrets/                   # 控制层密钥映射（严格权限）
  rooms/
    <immutable-room-id>/
      config/                   # 此房间的配置
      secrets/                  # 此房间的身份/模型凭据引用
      data/                     # Serein DB、索引、任务状态、运行文件
      backups/                  # 此房间的备份文件
```

不得使用用户输入的显示名称直接拼接磁盘路径；`room_id` 由服务端生成并按安全格式校验。任何配置复制、恢复、清理或更新都不能越过本房间的目录边界。日志须区分房间但遮盖 Key 和个人内容。

## 5. 请求路由与鉴权

### 5.1 Chat API

- 对外保持便利的 OpenAI 兼容入口（例如 `https://host/v1`），可由不同 **Gateway Key** 自动分流到对应房间。
- 每个房间单独生成 Key，管理员可查看一次、独立轮换、吊销。控制层持久保存安全的不可逆 Key 验证材料或受保护的秘密引用，而不是明文写在代码库与日志中。
- 网关验证 Token → 获得唯一 `room_id` → 校验房间状态 → 转发到该房间内部 Serein 服务。不得从请求模型 ID 推断房间。
- `X-Serein-Window-ID` 继续保留为**当前房间内部的会话/窗口标识**：同一房间的不同聊天窗口用不同值。它不负责跨房间认证。请求体既有 `serein.window_id` 兼容不受破坏。
- 当请求携带 `room_id` 指示或房间专属路径时，必须与已认证身份一致，否则拒绝；不能自动改路由。
- `/v1/models` 应只返回已鉴权房间配置的模型列表，不得泄露其他房间的模型设置。聊天归档、记忆注入、receipt/cooldown 均属于当前房间。

### 5.2 MCP（工具权限和调用）

- 新建一个房间 **不等于生成新的 MCP 工具实现**。各房间复用原版 Serein 的工具注册逻辑，但必须绑定各自的 `Application/Settings/DB` 与服务进程。
- 每房间保留既有「功能开关」及其生命周期；另提供按房间管理的 MCP `tools` 白名单。白名单默认可以从模板房间复制（可手动改），实际可用工具是**该房间已装载工具 ∩ 原版功能开关允许的工具 ∩ 该房间 MCP 权限**。
- 服务器同时约束 MCP `tools/list` 与 `tools/call`；即便 AI 手动构造调用被禁用的工具，也必须拒绝执行。权限修改应让下一次列举生效，并妥善处理旧会话的缓存和正在执行的请求。
- MCP 静态 `Bearer` Key 和聊天 Key 可以按现有 Serein 兼容策略在**同一房间内**共享，但绝不跨房间共享。
- **OAuth 是必需处理的兼容问题**：原版 OAuth 授权、资源元数据及 token 绑定单实例入口。多房间必须正确区分 OAuth resource/audience、授权实例与已发 Token。建议使用明确的房间专属 MCP 路径（例如 `/rooms/<room_id>/serein/mcp`）进行 OAuth 发现，并确保该路径身份与 token 绑定。全局 MCP 静态 Bearer 入口可以继续按 Key 自动路由。不得把一个房间的 OAuth 凭证当成另一个房间的凭证。
- 不得把敏感 Key 放到 URL 查询参数；使用 HTTPS 或安全本机通道。OAuth 兼容没有实现及测试通过前，**不得宣称远程 OAuth 已支持多房间**。

### 5.3 管理员与 AI 认证分离

管理网页登录凭据、API Gateway Key、MCP OAuth 凭据是不同安全主体。即便管理员正在查看某房间网页，后台接口也必须鉴别当前管理员权限和目标房间上下文，不能只依赖前端当前选中的房间名称。

## 6. 管理网页与交互

**统一网站结构：**

- 顶部/侧栏房间切换器：显示名称、运行状态、房间 ID 摘要；支持增加、重命名、暂停、恢复、查看状态；删除属于危险操作，须强确认并展示备份风险。
- 选中房间后展示原版 Serein 的全部现有功能页面，并将请求绑定选中房间；**尽量复用现有页面，不重新写一套 UI**。
- 「设置 → 功能」：每房间原有功能开关，包含日记、梦境、自动摘要等相关配置。
- 「设置 → MCP 工具权限」：每房间单独工具清单、选择与保存；工具开关跟功能开关分开显示。支持一键全选/重置到模板（须确认），工具实际可见状态从当前房间 `tools/list` 或服务端规则取得。
- 「设置 → 模型 / 配置」：每房间的模型上游和任务角色配置可以分别修改，修改 A 不得更改 B。
- 「备份与恢复」：每房间分别查看备份、创建、下载、校验和恢复。
- 「运行状态」：分房间查看服务健康、后台队列、索引状态、最近错误和资源占用，不展示敏感材料原文。
- 网页功能优先；VPS/CLI 提供与管理层共享业务逻辑的等效操作，避免维护两套不同的数据操作实现。

**不得**用仅在浏览器 localStorage 中切换 room 来冒充权限隔离；服务端每次管理请求都必须明确并认证目标房间。

## 7. 新建房间流程：默认配置复制

### 7.1 创建方式

管理员在网页点「添加 AI 房间」，或者通过 VPS 管理命令执行等效操作（具体 CLI 命名待实现，例如 `serein rooms create`，不是原版现有命令）。创建界面输入房间名称，选择配置来源：

1. **默认：复制第一个房间的配置**。控制层可提供 `default_template_room_id`，首次创建房间后自动指定首房为模板；若模板不存在或停止可读，必须明确提示，不得暗中复制其他房间。
2. **复制其他指定房间的配置**。
3. **空白初始化**，不复制模型/上游及权限配置。

单独提供「是否复用模型服务商秘密凭据」选项；复制配置前须明示：复用凭据可能共享厂商额度和速率限制，但每房间的 Serein 数据依然隔离。模型密钥可选择复用受保护的秘密引用，而不是复制明文文件。

### 7.2 允许复制 / 禁止复制

| 可复制的**配置**（按管理员选择） | 严禁复制的**私人数据或身份** |
|---|---|
| 模型上游定义、模型 ID、别名和参数 | 原话、聊天历史、用户/AI 私人资料 |
| 聊天与任务模型角色选择 | Event、Scene、叙事卷及原文证据 |
| 召回相关的阈值/功能参数 | 日记、暗房、梦境、备忘、窗影 |
| 原版功能开关和计划运行策略 | 索引内容、向量、召回冷却与任务/队列进度 |
| MCP 工具白名单模板 | 旧 Gateway Key、OAuth token、网页登录凭据 |
| 可选的模型服务商凭据引用 | 备份、历史日志、房间秘密与运行缓存 |

注意：一些 Serein 功能设置目前存储在实例数据库内，不能通过**复制 SQLite 文件再删表**来充当干净的配置模板。需要做专门的 **配置白名单导出/导入或干净新库初始化**，只传允许的字段；对用户名、角色身份、日记 Prompt、个人化指令、模型参数中的私密信息进行字段级审查，存在歧义时默认不复制，显式询问管理员。新房间必须保留空白私人数据。

### 7.3 原子化创建要求

校验名称和模板 → 生成不可变房间 ID → 生成全新网关身份 → 创建空白持久目录与配置 → 初始化空库和独立服务 → 健康检查 → 注册路由 → 将状态标为 ready → 展示接入信息。某一步失败则进入清晰的 `error` 状态并可安全重试/清理；不得留下错误指向其他房间的路由。

## 8. 数据、后台任务与性能隔离

- 每房间独立 SQLite 数据库、独立索引、独立备份和运行目录；数据库打开、模型选择、索引 worker、自动摘要队列与任务锁都由房间自己的配置确定。
- 选用每房间独立服务进程/容器来获取清晰的崩溃边界；一个房间发生 Python 异常、任务失败、索引暂停，不应修改其他房间状态或直接重启其他房间。
- 调度需设置合理的 per-room CPU/内存限制、后台作业并发限制、队列长度和超时；网关对过载返回明确错误而不是发错房间。
- 多个房间复用同一个 Embedding/LLM 供应商 Key 时，调用费用和供应商速率限制可能相互影响；UI/文档必须说明这种边界，不能保证第三方额度隔离。
- 房间停止后不应继续执行其后台任务；恢复后应按该房间原有持久任务状态继续，不自动把失败任务移动到其他房间。

## 9. 备份、恢复、迁移

- 每份备份要包含恢复该房间所需的**完整状态**：Serein 主数据库、向量及索引文件、必要的辅助运行文件、该房间的模型/功能/扩展配置及可安全导出的密钥引用信息；明确列出不能自动打包的外部秘密及恢复后的重新授权步骤。
- 备份清单 `manifest` 至少包含 `room_id`、房间显示名（仅用于展示）、创建时间、应用版本、schema 版本、文件清单/校验摘要、备份格式版本。密钥与记忆文件应遵守严格访问控制，必要时加密；不写入 Git。
- SQLite 备份必须遵循一致性操作（例如 SQLite backup API 或明确的停止/快照阶段），不能在数据库活跃写入时简单打包并声称成功。
- 恢复前校验清单、文件校验和、版本兼容性、目标 `room_id`；默认禁止跨房间覆盖。恢复前先给目标房间做安全快照，失败要能够回到之前状态。
- 兼容单实例 Serein 的已有用户应可以将原实例**原样纳入首个房间**，但必须先备份和核对路径；不要擅自清空、移动、初始化旧数据库。首次 MVP 可先完成空实例新增，再专门做迁移工具。
- 删除房间时：区分停用、取消注册、彻底清理数据；永久删除需二次确认，说明对备份的影响。不得使用危险的递归路径拼接影响其他房间。

## 10. 更新、同步原作者与回滚

### 10.1 上游关系

- GitHub Fork 为 `qiq-Blanchet/Serein-MultiRoom`；`main` 尽量保持便于与 `Yinglianchun/Serein` 同步的原版基线，多房间功能在 `feature/multi-room` 上开发，经过测试后再决定如何创建稳定发布分支/标签。
- 同步原作者更新不是直接用原作者的安装脚本覆盖运行目录。应先拉取上游提交，在 Git 工作区合并/变基并修复冲突、运行测试，然后从**本 Fork 的已验证版本**构建镜像及部署。
- **特别检查原版 `scripts/upstream_update.py`、交互安装脚本和发行 manifest**：原版自动更新默认可能拉取 `Yinglianchun/Serein/main`。必须改造成受控的 Multi-Room 更新流程，禁止直接使用会覆盖自定义改造的更新命令。
- 仓库中的新源文件、部署文件及文档若要参与原版发行机制，需要检查并更新 `release-files.json` 等显式清单；不要依赖“文件在 Git 里就会自动进入发行包”。

### 10.2 统一更新与逐房间迁移

1. 管理层展示旧版本、目标版本、变更及影响房间数。
2. 先备份所有待更新房间并校验可读性；若有备份失败，停止进入更新。
3. 构建/拉取一个已测试版本的**共享代码镜像**，不要按房间各维护一份源码。
4. 一个房间一个房间停止、迁移、启动、健康检查（包含 Chat/MCP、基础读写、索引兼容），确认通过后更新下一个房间。
5. 如果某个房间失败，暂停后续房间更新，记录失败原因；在兼容性允许且备份完整时恢复该房间状态。**不能声称仅切回镜像就能回滚数据库 schema**。
6. 允许查看各房间的当前实际版本和升级状态，避免管理网页以为所有房间都更新成功。

## 13. 验收标准（必须自动化验证的核心场景）

### 13.1 房间隔离

- [ ] 创建房间 A、B、C；分别写入同名 Scene、日记、梦境等后，只能在各自房间读到自己的数据。
- [ ] A 的聊天和 MCP 请求不能读取/修改 B 的记忆、原话、备忘、索引任务、备份；B 同理。
- [ ] A 的 Key 搭配 B 的路径、房间 ID 或 Window ID 被拒绝；不能静默误路由。
- [ ] 同一个模型 ID 在两个房间使用不会引发数据合并；`/v1/models` 也只显示所属房间配置。
- [ ] A 的索引暂停/自动摘要失败/服务崩溃不修改 B 的作业状态；B 的服务仍可使用（共享 VPS 资源限制范围内）。

### 13.2 工具与功能

- [ ] A 打开 `dream_read`、B 关闭 `dream_read`：B 的 `tools/list` 不包含它；强行 `tools/call` 返回拒绝且无副作用。
- [ ] 关闭 A 的 MCP `write_diary` 不会删除 A 已有日记，也不会自动关闭原版允许的其他后台流程。
- [ ] 关闭原版某功能后，不能通过 MCP 权限绕过该功能的原版开启条件。
- [ ] 权限更改后，新会话和已连接客户端的工具调用按服务器最新规则受限。

### 13.3 创建与复制

- [ ] 默认复制首房可复用模型及功能配置，并生成**新的** Key、空白数据库、独立索引/任务状态。
- [ ] 可以选择其他房间、可以空白创建、可以选择是否复用模型厂商凭据。
- [ ] 创建中途失败不留下能访问别的房间的错误路由、目录或可用凭据；重试不重复创建。

### 13.4 备份/更新/兼容

- [ ] 每份备份携带不可变 room ID、版本和校验信息；把 A 的备份误恢复到 B 必须拒绝。
- [ ] 恢复 A 不改变 B 的数据、索引或模型设置；备份/恢复失败不影响其他房间。
- [ ] 发布一次新程序版本后可分批升级，单房间失败能暂停后续升级并保护现有数据。
- [ ] 原版 Chat API 的窗口/续接行为、MCP 静态 Key 与（最终阶段的）OAuth 按房间正常工作。
- [ ] 关键原版回归测试通过，尤其召回、证据、Writer、Event、索引、MCP 工具和权限测试。

## 14. 开发协作规则（给后续 AI/开发者）

1. **开始任何 Multi-Room 开发前，先读本文件和仓库 `AGENTS.md`。** 以用户已经确认的要求为准，不反复重新发明架构。
2. 所有功能开发只提交到 `feature/multi-room`（或基于它的明确功能分支）；**不要未经授权修改 `main` 或上游仓库**。
3. 修改前查看当前源码、对照具体接口；不要只凭设计文档猜测原版 API 细节。
4. 优先在控制层/网关/部署层实现隔离，尽量减少核心记忆算法的侵入性改动。
5. 每次代码提交应附对应测试、所修改模块及阶段说明；对数据结构、认证或备份的变更补充失败路径测试。
6. 新增或变更架构性决策，先在本文新增「决策记录」并注明日期、原因、取舍，再实施；不要让口头临时方案覆盖本文件。
7. 不得提交明文 API Key、模型密钥、私人数据库、日志原文、备份或 `runtime/`；用合成 fixtures。
8. 开发完成一次阶段后更新下方进度，避免后续会话误以为所有功能都已实现。
